## 一句话

**CodeRev 是开源免费的 PR 审查与测试闭环工具**，自托管运行，数据不出内网。
产品策略是**先做变更追溯（B），再做 PR 审查（A）**——因为审查工具已经很多，而"这个 PR 服务哪条需求、这条需求改过几次"没人管。

---

## 我们要解决的问题

1. **评审是瓶颈**。10–50 人团队只有 2–3 个能拍板的 reviewer，PR 从提交到被认真看要 4–24 小时，于是团队"先合再修"。
2. **需求频繁变更，项目组靠开会兜底**。客户通过项目经理提变更 → 项目组开会分析 → 出变更单 → 定级。整个过程没有工具，全靠人记。
3. **审查与测试割裂**。审查说"这儿没测"，测试说"覆盖率够了"，两边不通。
4. **交付质量无法度量**。外包场景里，甲方只能验收"能跑"，无法验收"可维护"。

---

## 两条轨道

| | **B 轨道：变更追溯** | **A 轨道：PR 审查** |
|---|---|---|
| 解决什么 | 变更从提出到签字的全链路留痕，影响面可查 | PR 自动审查、风险摘要、测试建议 |
| 形态 | 变更单 + 台账 + 周报 + 汇总（Excel + Word） | GitHub Action / 自托管（Docker） |
| 门槛 | 明天就能开始 | GitHub App 审核 1–2 周 + 评测集 |
| 状态 | **观察期（2 周），人工跑流程** | **PRD 已完成，代码未开始** |
| 文档 | `docs/b/` | `docs/a/` |

**为什么先 B**：B 两周能验证，且它产出的「变更 ↔ 模块 ↔ 需求」数据，是 A 唯一难以被同类产品替代的东西。只做 A，就是"又一个 AI 审查工具"。

## 已锁定的决策

### 流程口径（改动需评审）

| 项 | 结论 |
|---|---|
| 报价 | 按合同单价**人工核定**，一律**不含税** |
| 客户确认时限 | **5 个工作日** |
| 超期处理 | 变更**挂起**，不进入排期 |
| 升级红线 | 挂起满 **10 个工作日** → 上报客户高层 |
| 澄清类 | 由**产品经理**确认，无需客户签字 |
| 台账粒度 | 每项目一份；跨项目**双周**人工汇总 |
| 变更编号 | `项目代号-CHG-YYYYMMDD-NN` |

### 产品与技术决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 先 B 后 A | 先跑变更追溯 | 建数据资产，避免被平替 |
| 审查底座 | PR-Agent（宽松许可，可自托管） | 不自研审查引擎 |
| 测试能力 | 自研测试建议 + 客户 CI 上报覆盖率 | **待重评**：项目转 AGPL 后，"规避 AGPL"的约束消失，可考虑接入 qodo-cover |
| 审查输入 | diff + 变更文件上下文，**不做全仓索引** | 控成本、控延迟 |
| 默认行为 | 只评论、**不阻断合并** | 降低试用阻力 |
| ~~计费~~ | ~~按 repo + PR 额度，不按 seat~~ | **已废止**：开源免费，无计费 |
| 契约 | 当前**不存在**，后续从代码反推 | 不逼团队先写 OpenAPI |

## 路线图

```
W1–W2    B 观察期（人工跑流程，攒 15–25 条变更数据）
W3       五项验收打分 → 决定是否进入自动化
         A 的六条判据同步推进（评测集、App 审核、种子客户）
W4+      A 开发（4 周 MVP）
之后     B 自动化：变更单入库 → 图谱 → 影响面引擎
```

## 术语

| 术语 | 含义 |
|---|---|
| **B / A** | 变更追溯（B）、PR 审查（A）两条轨道 |
| **变更单** | 一次变更的结构化记录，兼作商务凭证（报价 + 客户签字） |
| **挂起** | 已定级但客户未在时限内确认的变更，从排期中摘出 |
| **AC** | 验收标准（Acceptance Criteria），需求可测试的最小断言 |
| **切片（slice）** | 按契约边界拆出的可并行开发单元 |
| **增量覆盖率** | 只看本次新增/修改代码行的覆盖率 |
| **误报率** | 被标记"不准确"的意见 ÷ 总意见数 |
