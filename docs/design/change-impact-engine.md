# 变更影响引擎设计（V2）

> 解决的问题：**需求一变，谁受影响、哪些用例失效、哪个契约破了、要多久。**
> 当前状态：设计稿。观察期（B）先手工攒数据，满足条件后再实现。

---

## 1. 为什么需要它

客户通过项目经理提变更，项目组开会定级——这条流程现在靠人。人能做，但做不快、记不住、传不下去：

- 改了需求，没人能说清影响哪几个模块
- 代码合了，没人知道对应哪条验收标准
- 联调挂了 50 个用例，没人能快速归类

---

## 2. 静态追溯 vs 变更驱动

| | 静态追溯（普通文档） | 变更驱动（本引擎） |
|---|---|---|
| 图谱 | 建一次，偶尔更新 | 每次变更都要**失效、重算、重验** |
| 审查标准 | 团队规范（相对稳定） | 规范 + **当前版本的 AC**（随时在变） |
| 测试 | 补单测 | 还要标记"哪些用例基于旧 AC 已失效" |
| 核心指标 | 误报率、采纳率 | **变更响应时间、返工率、变更引发的缺陷率** |
| 本质 | 文档 | **影响面计算 + 一致性维护** |

---

## 3. 五个机制

### 3.1 需求版本化，变更用 diff 表达

不能覆盖式更新。`REQ-123 v3 → v4` 必须产出结构化 diff：新增 2 条 AC、修改 1 条、删除 1 条。没有 diff，就没有影响面计算。

### 3.2 变更意图分类，决定处理路径

| 类型 | 处理 |
|---|---|
| 新增 AC | 需要新切片/新用例，通常不影响存量 |
| 修改 AC | 存量用例**失效**，相关切片要重审 |
| 删除 AC | 相关代码和测试变"孤儿"，可做死代码检测 |
| **澄清（语义不变）** | 只更新文档，不触发任何重跑 |

> 客户 80% 的"变更"其实是澄清。不能自动识别，工具会被噪音淹没。这里必须有人确认环节，AI 只做初判。

### 3.3 影响面传播要带置信度

图谱上反向可达：`AC → 切片 → PR/代码符号 → 测试用例 → 业务流`

| 来源 | 置信度 |
|---|---|
| PR 里显式声明 `slice_id` | 1.0 |
| 静态调用链 | 0.8 |
| LLM 语义匹配 | 0.6（低于阈值必须人工确认） |

**漏判比误判危险得多**——漏了会给人虚假的安全感。宁可多列"待确认"，也不要静默跳过。

### 3.4 契约变更是最高优先级信号

客户改需求 → 大概率改接口（加字段、改枚举、改错误码）。这类变更要立刻标红：breaking / non-breaking，影响哪些调用方、哪些契约测试、哪些 flow。

**当前没有契约怎么办**：从代码反推"事实契约"——HTTP 路由 + 请求/响应 DTO、DB 表结构与迁移文件、消息 topic + payload、错误码枚举。生成契约快照 vN，每次变更对比快照即可做 breaking 检测。**先观测、再治理**，不逼团队先写 OpenAPI。

### 3.5 增量验证 + AC 满足矩阵

不重跑全量，只跑受影响切片 + 受影响契约 + 相关 flow。产出是一张表：

| AC | 切片 | 状态 |
|---|---|---|
| AC-1 | 订单 | ✅ 通过 |
| AC-2 | 支付 | ⚠️ 用例失效（基于旧 AC） |
| AC-3 | 对账 | ❌ 未覆盖 |

这张表就是拍板人要看的东西。

## 4. 数据模型（图谱）

```
Requirement (REQ-xxx, version)
    └── AcceptanceCriterion (AC-xxx-n, version, testable statement)
            └── Slice (SL-xxx-a)
                    ├── Contract (endpoint / event / table / field, version)
                    ├── CodeUnit (repo, path, symbol, commit)
                    └── TestCase (unit / contract / flow)
                            └── Flow (business flow, 引用多处 contract)
```

边上带属性：`source`（声明/静态/语义）、`confidence`、`updated_at`、`stale`（是否因变更失效）。

## 5. 一个例子

客户说："要支持多币种。"

引擎应在一轮里给出：

```
变更：REQ-123 v4 新增 AC-7「订单支持多币种结算」
影响面：
  切片 3 个 —— 订单(高)、支付(高)、对账(中)
  契约 1 处 —— Order.amount 需增加 currency 字段（breaking）
  用例 12 条失效 —— 其中 7 条基于旧金额假设
  业务流 2 条受影响 —— 下单支付、日终对账
  工作量预估 4.5 人日；风险：历史数据迁移未覆盖
建议：先做契约评审再进开发（否则三个切片会各写一套币种逻辑）
```

价值不在"预测准不准"，而在**逼着团队在动手前把话说清楚**——这就是拍板的材料。

---

## 6. 三条硬约束

1. **"实时调整" ≠ 自动改代码**。能做的是秒级告诉你"哪里受影响、哪些用例失效、哪个契约破了"，改还是人改。
2. **图谱一定会腐烂**。靠人手工维护映射，两周就没人更新。必须自动建图（PR 声明 + 代码分析 + 契约同步）+ 每周一致性巡检。
3. **变更闸门是流程问题**。工具能给影响面，但如果变更单不需要附影响面就能进开发，一切白搭。

---

## 7. 实施阶段

| 阶段 | 内容 | 前提 |
|---|---|---|
| P1 | 变更单结构化入库 + 自动周报 | 观察期数据 |
| P2 | 代码侧契约快照 + breaking 检测 | 仓库读权限 |
| P3 | 影响面预测 + 与 A 的审查打通 | P1/P2 数据积累 |

**进入 P1 的判定**：观察期五项里三项达标（完整率 ≥80%、估算偏差 ≤40%、材料使用率 ≥70%、会议时长降 ≥15%、澄清占比可解释）。

---

## 8. 与现有 B 模板的衔接

| 现有字段 | 喂给引擎什么 |
|---|---|
| 客户原话 | 意图分类训练语料 |
| 变更类型 + 受影响模块 | 图谱的第一批边 |
| 工作量三档 vs 实际 | 估算校准系数 |
| 建议等级 vs 最终等级 + 改判理由 | 定级规则调参 |
| 关联需求 ID + AC 变化 | 需求图的主键关联 |

> 换句话说：**B 现在填的每一个字段，都是这个引擎未来的训练数据。** 这就是为什么表单字段值得较真。
