# 开源化改造：设计变更清单

> 背景：项目从「SaaS 订阅」转为「开源免费」。
> 结论先行：**去掉商业化不是删几章，它会反向简化架构**——多租户、计费、额度、试用漏斗全部失去意义，而部署形态、License、社区治理变成新的设计核心。

---

## 0. 一句话结论

原来按「卖给 10–200 人团队的 SaaS」设计的东西，现在要按「**别人能自己跑起来、能贡献、能长期维护**」重新设计。前者优化转化率，后者优化**首次成功时间**（从 clone 到看到第一条 PR 评论）。

---

## 1. 影响面总览

| 设计项 | 原方案（SaaS） | 开源后 | 动作 |
|---|---|---|---|
| 商业模式 | 订阅 + 额度 + 超额计费 | 免费，靠赞助/托管/商业许可 | **重写** |
| 部署形态 | 多租户 SaaS | 单租户自托管 + GitHub Action | **重设计** |
| 多租户 | `tenant_id` + RLS | 单组织，无需隔离 | **删除** |
| 计费 | Stripe/微信、订阅表、额度扣减 | 无 | **删除** |
| LLM 成本 | 平台承担，租户预算 | 部署方 BYOK 承担 | **反转** |
| 指标 | 试用转化、churn、ARPU | 安装量、贡献者、采纳率 | **替换** |
| License | 只需规避 AGPL | 自己就要选一个 | **新增决策** |
| 规则配置 | 控制台 UI | YAML + git（rules-as-code） | **改形态** |
| 支持 | 分级支持 + SLA | Best effort + Discussions | **降级** |
| 私有化 | Enterprise 加价项 | 默认形态 | **升为主线** |
| 审查流水线 | — | — | **不动** |
| 误报治理 | — | — | **不动（仍是核心）** |

## 2. 五个必须做的决策

### 2.1 License：三选一

| 选项 | 好处 | 代价 | 适合 |
|---|---|---|---|
| **MIT / Apache-2.0** | 传播最快，企业最放心 | 别人可以闭源套壳做成 SaaS，与你竞争 | 目标是"影响力"而非"护城河" |
| **AGPL-3.0** | 谁拿去做网络服务都必须开源改动；**顺便解锁 qodo-cover 依赖** | 部分企业法务直接禁 AGPL | 目标是"防止被白嫖"，且自托管为主 |
| **Apache-2.0 + 商业许可双轨** | 社区版宽松，闭源商用需付费 | 需要运营商业许可，复杂度上升 | 想留后路 |

**推荐：核心服务用 AGPL-3.0，规则包 / CLI / SDK 用 Apache-2.0。**

理由：

1. 这是**服务端产品**，价值在整套系统，不在某个库；MIT 会让"套壳 SaaS"成为最优策略。
2. 自托管是主要形态，用户拿不到源码也无所谓——AGPL 对他们的实际约束很小。
3. **原方案为了规避 AGPL 放弃了 qodo-cover**；现在自己就是 AGPL，这个约束消失，测试生成能力可以重新评估。
4. 给不能接受 AGPL 的公司留一条**商业许可**的口子，将来是唯一自然的收费点。

> 注意：如果最终选 Apache，就必须继续维持"不引入 AGPL 依赖"的设计约束——这是两个方案的分水岭，先定这个再动代码。

### 2.2 部署形态：三个入口，按成本排序

| 形态 | 适合谁 | 成本 | 优先级 |
|---|---|---|---|
| **GitHub Action** | 个人 / 小团队 / 开源项目 | 零服务器，用仓库自己的 minutes | **P0** |
| **Docker Compose 自托管** | 团队 / 内网 / 私有仓库 | 一台机器 + BYOK | **P0** |
| **Helm / K8s** | 中大型组织 | 集群 | P1 |

**关键判断**：开源项目的第一次成功不是"注册"，是"5 分钟内跑出第一条评论"。所以 **Action 形态必须存在**——它把"装一个 App"降到"加一个 workflow 文件"。

### 2.3 成本承担：谁付 token 钱

- **自托管**：部署方 BYOK（OpenAI / Anthropic / DeepSeek / 本地模型），平台零成本。
- **官方托管 demo**：只做 BYOK + 严格限流，或**干脆不做**——否则一个热门仓库就能烧掉一个月预算。
- **GitHub Action**：用户自己的 secrets，成本天然隔离。

> 这一条把原 PRD 里最头疼的"单 PR 成本 / 毛利"问题直接消掉了。**免费开源反而让单位经济变简单了。**

### 2.4 社区治理：先定"不做什么"

开源项目死于范围膨胀，不死于功能少。发布前就要写清楚：

- **明确不做**：IDE 插件、代码托管、自动合并、通用代码补全。
- **接受贡献的边界**：规则包、模型适配、平台集成欢迎；核心流水线改动需要 maintainer 讨论。
- **决策机制**：`GOVERNANCE.md` 写清楚谁有 merge 权、如何成为 maintainer。

### 2.5 商业化残余：只留三个口子

| 口子 | 形态 | 何时启用 |
|---|---|---|
| 赞助 | GitHub Sponsors / Open Collective | 发布即开 |
| 商业许可 | 给不能接受 AGPL 的公司 | 有第一个问的人再开 |
| 托管/落地服务 | 帮客户部署 + 变更流程咨询（B 轨道） | 有需求再谈 |

**不做**：付费档位、功能阉割版、白标加价。开源项目一旦做"社区版 vs 企业版"，信任成本极高。

## 3. 架构简化

### 删除

- 计费服务、订阅表、额度扣减、超额计费
- 多租户：`tenant_id`、RLS、租户 onboarding 向导
- 控制台的规则配置 UI（改为 YAML）
- 白标报告、套餐页、试用漏斗埋点

### 保留（一行不改）

- 审查流水线：webhook → 队列 → worker → PR-Agent runner → LLM → 评论
- 输出契约（JSON schema）、行号校验、置信度阈值、去重指纹
- 严重级别三级、默认不阻断
- 覆盖率上报 API + 增量计算
- 评测集与回归门禁

### 新增

| 组件 | 说明 |
|---|---|
| GitHub Action 入口 | 一个 `action.yml` + 容器镜像 |
| CLI | `coderev review --pr 123`，便于本地和 CI 调试 |
| Docker Compose | 一份 `docker-compose.yml`，含 Postgres/Redis |
| Helm Chart | P1 |
| 配置即代码 | `.coderev.yml` + `rules/*.yaml`，随仓库走 |
| 匿名遥测（opt-in） | 默认关闭，文档写明收集什么 |
| 部署文档 | `docs/deploy/action.md`、`docker.md`、`k8s.md` |

### 数据模型变化

- 删：`tenants`、`subscriptions`、`usage_events`（计费用）、`memberships` 的角色体系
- 留：`repositories`、`review_runs`、`findings`、`feedback`、`coverage_reports`
- 改：`rule_packs` 从数据库表改为**仓库内的 YAML 文件**（可 diff、可 PR、可评审）

> 规则从数据库搬进 git，是开源化最划算的一步：社区贡献规则 = 提 PR，不需要 UI，也不需要迁移脚本。

## 4. PRD 逐章改动

| 章节 | 改动 |
|---|---|
| 1 背景与机会 | 去掉市场规模/付费意愿论证，改成"为什么这件事该开源" |
| 2 定位 | "SaaS"→"开源自托管"；反定位补充"不做托管 SaaS" |
| 3 用户场景 | 增加 Persona：开源维护者（现在是**首要用户**，不是种子用户） |
| 4 指标 | 删除转化/churn/成本占比，替换为采用与社区指标 |
| 5 范围 | 删除计费、多租户、白标；增加 Action/CLI/部署 |
| 6 功能 | 删除 6.8 计费；6.2 规则中心改为"规则即代码" |
| 8 非功能 | 删除租户隔离；安全章节加重（自托管者会暴露 webhook） |
| 9 技术方案 | 简化为单租户；增加部署拓扑 |
| 10 License | **从"合规约束"升级为"核心设计决策"**（见 2.1） |
| 11 商业化 | 整章重写为"开源运营与可持续性" |
| 12 里程碑 | 4 周 MVP 改为"发布 v0.1 的 4 周" |

## 6. 指标替换

| 删除 | 替换为 |
|---|---|
| 试用转化率 | 首次成功时间（clone → 第一条评论） |
| 月流失 | 周活跃安装数（opt-in 遥测） |
| ARPU / 毛利 | Star / Fork / 贡献者数 |
| LLM 成本占比 | Issue 首次响应时长 |
| 单 PR 成本 | PR 审查数、意见采纳率 |

北极星可以保留"**周活跃审查 PR 数**"——它对 SaaS 和开源都成立。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 被闭源套壳做 SaaS | AGPL（选 Apache 则无解，需接受） |
| 维护者倦怠 | 发布前写死"不做清单"；issue 模板强制复现步骤 |
| 自托管安全事件 | 默认安全配置、强制 webhook 验签、不执行客户代码、SECURITY.md |
| 提示注入（PR 内容含恶意指令） | 审查 worker 只读不执行；输出经 schema 校验；不把 PR 文本当指令 |
| 规则质量参差 | 每条规则必须带 golden test（样例 PR + 期望结果） |
| Fork 分裂 | 商标政策 + GOVERNANCE 明确"官方"定义 |
| 免费额度被滥用（若做托管） | 只做 BYOK + 限流，或不做托管 |

## 8. 迁移顺序（4 周）

| 周 | 做什么 | 产出 |
|---|---|---|
| W1 | 定 License；删 PRD 商业化章节；仓库加 LICENSE/CONTRIBUTING/SECURITY | 法务与定位就绪 |
| W2 | 拆出 Action 形态；Docker Compose 跑通 | 别人能装 |
| W3 | 规则即代码（`rules/` + golden test）；CLI | 别人能改 |
| W4 | 部署文档、ROADMAP、公告稿；发布 v0.1 | 对外发布 |

## 9. 待确认

1. **License 选哪个**（AGPL / Apache / 双轨）——这一条决定后面全部技术约束。
2. 是否保留**官方托管**（哪怕小规模）？涉及成本与滥用。
3. 目标用户优先级：开源维护者优先，还是企业内网优先？
4. 是否接受"社区版 / 企业版"双轨（我建议不要）。
5. 现有 B 轨道（变更管理）是否也开源？它是**方法论 + 模板**，开源能带来差异化，但也是你们咨询业务的本体。
