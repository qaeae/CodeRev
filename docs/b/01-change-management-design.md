# 需求变更管理设计 v0.1（观察期版）

> 适用阶段：**先观测 2–3 周，不改流程**。本文件定义变更单、定级规则与观察方案，观察期结束后再决定自动化做什么。

---

## 0. 结论先行

1. **变更单是数据入口，不是审批表**。填一次，同时服务三件事：会上决策、事后统计、未来训练影响面模型。
2. **不要算"延期几天"，要算"吃掉多少冗余"**。你们排期本身就留了缓冲，直接报延期会失真，也会引发无谓争论。
3. **观察期的唯一目标**：证明"会前 5 分钟的材料"能缩短会议、减少返工。证明不了，自动化就是空中楼阁。

---

## 1. 现状与约束

| 事实 | 推导出的设计约束 |
|---|---|
| 客户通过项目经理提变更 | 变更单必须有"客户原话"字段，且不得改写——这是后续判定意图的唯一原始证据 |
| 客户不参加分析会，项目经理只做过滤和转达 | 必须有"需转达客户的澄清项"字段；会上没有客户，任何"客户应该是这个意思"的判断都要落成待确认项 |
| 需要项目组开会分析后产出变更单 | 变更单是**会议的产物**，不是会前问卷；会前只需给"初判"，会上再补全 |
| 产品经理先把关 | 需要一道"预审"闸门，5 分钟内判断：澄清 / 变更 / 新建，要不要开会 |
| 契约现在不存在 | 影响面只能到"模块/切片"级，接口级标注"待梳理"，不假装精确 |
| 排期有冗余，是否影响由会议决定 | 排期影响用区间 + 冗余消耗率表达，决策权留给人 |
| 分析会一周一次 | 工具节奏是**周更**，不是实时推送；周中只做登记，会前批量生成材料 |

## 2. 变更单设计

### 2.1 一句话原则

**8 分钟能填完，会上能直接念。** 超过 8 分钟，第二周就没人填了——这是所有变更管理工具的死因。

### 2.2 字段结构（七段，A–G）

| 段 | 字段 | 谁填 | 必填 | 用途 |
|---|---|---|---|---|
| **A 基本信息** | 变更编号、提出日期、项目、客户、提出人、转达人、变更标题 | 项目经理（登记） | 是 | 定位与追溯 |
| **B 变更内容** | **客户原话**、变更类型、紧急程度 | 项目经理（登记） | 是 | 判定意图的唯一原始证据 |
| **C 需求关联** | 关联需求 ID、AC 变化（新增/修改/删除）、是否更新 PRD、影响章节 | 产品经理（预审） | 是 | 把变更挂到需求图上 |
| **D 影响分析** | 受影响模块（确认/疑似）、接口与数据表、数据结构变更、对外 breaking、用例数、回归流程、工作量三档、排期影响、未知项、**需转达客户的澄清项** | 项目组（会上） | 是（澄清类可跳过） | 定级的输入 |
| **E 定级与决策** | 六维评分、评分依据、建议等级、最终等级、改判理由、决策、决策人、客户是否确认范围 | 项目组（会上） | 是（澄清类可跳过） | 决策记录，可审计 |
| **F 执行与关闭** | 派生任务、实际工作量、实际排期影响、是否线上问题、一句话复盘 | 项目经理（关闭时） | 否 | 校准未来估算 |
| **G 商务与客户确认** | 计费方式、报价（按合同单价人工核定）、确认时限与截止日、客户确认方式、签字/盖章/日期、澄清类确认人 | 项目经理（会后） | 是 | 客户不参会，必须独立留痕 |

> 澄清类走的是"短路流程"：B → C → G，跳过 D/E。这样一条澄清 3 分钟能处理完，不会挤占会议时间。

### 2.3 关键字段的取值设计

**变更类型**（决定后续处理路径）
`新增功能` / `修改功能` / `删除功能` / `澄清（无功能变化）` / `缺陷转需求`

> "澄清"必须单独一类。客户 80% 的"变更"其实是澄清，混在一起会让所有统计失真。

**紧急程度**（客户主张，与最终等级分开）
`普通` / `紧急` / `特急`

> 客户永远说特急。分开记，三个月后就能拿出"客户主张特急 vs 实际定级"的对比，用于谈判。

**数据结构变更**
`无` / `新增字段` / `修改结构` / `需迁移历史数据`

**排期影响**（对应你们"有冗余"的实情）
`不占关键路径` / `吃掉冗余 ≤50%` / `吃掉冗余 >50%` / `需顺延 N 天` / `需重排里程碑`

**决策**
`本期做` / `下期做` / `拆分做` / `不做（转商机）` / `待客户确认`

**计费方式**
`含在原合同` / `按人日` / `固定总价` / `需签补充协议` / `不涉及`

**客户确认方式**
`现场签字` / `邮件确认` / `补充协议` / `产品经理确认` / `不涉及`

**确认时限与挂起规则**
- 每张变更单填「约定 5 个工作日（默认）」和「确认截止日」。
- **截止日未收到客户确认 → 状态改为「挂起（待客户确认）」，不进入开发排期，不占用人日。**
- **挂起满 10 个工作日 → 自动标记「需升级」，由项目经理上报客户高层，状态改为「已升级（客户高层）」。**
- 客户确认后：状态转「执行中」，回填客户签字日期；台账自动算出「确认用时(天)」。
- 澄清类不进这条链路：由产品经理确认即可，台账"客户确认"填「产品经理确认」。

> 两个数字是分开的：**5 个工作日是客户承诺的响应期，10 个工作日是升级的红线。** 只设一个数字，要么太软（客户拖三周才升级），要么太硬（第 6 天就惊动高层，关系搞僵）。

> 这条规则是整个表单里唯一带"牙齿"的：没有它，签字就是一句客气话；有了它，客户拖延会让变更自己停下来，而不是让开发背锅。

**编号规则**
`项目代号-CHG-YYYYMMDD-NN`，例如 `PRJ-A-CHG-20251109-01`。带项目代号是为了跨项目引用时不用查表——外包场景经常要在不同项目间比对变更量。

### 2.4 字段背后的四个"私心"

1. **客户原话**——将来判"澄清还是变更"，这是唯一证据；也是训练意图分类模型的语料。
2. **实际工作量 vs 估算**——观察期最重要的产出，用来校准估算偏差（多数团队低估 30–50%）。
3. **改判理由**——建议等级与最终等级不一致时必填。半年后这份数据能告诉你：工具的定级规则哪里偏了。
4. **报价与签字单列一段（G）**——客户不参会，商务动作一定发生在会后。如果和影响分析混在一起，就会出现"会开完了，单子还没签"的真空期。单列之后，变更单同时是**变更的商务凭证**，而不只是技术记录。

## 3. 生命周期

```
登记(PM) → 预审(产品经理) → 分析会(项目组) → 定级(会上) → 决策 → 执行 → 关闭
              ↓ 澄清类                    ↓ 不做
          直接关闭(留档)              转商机/待确认
```

状态值：`登记` / `预审中` / `待上会` / `已定级` / **`挂起（待客户确认）`** / **`已升级（客户高层）`** / `执行中` / `已完成` / `已关闭(澄清)` / `已取消`

**挂起是正常状态，不是异常。** 定级完成后进入"待客户确认"，超过约定时限未确认即转"挂起"，从排期里摘出来；确认后回到"执行中"。这条路径必须在流程图里画出来，否则团队会把它当成"卡住了"去催，反而失去意义。

**周节奏**

| 时间 | 动作 | 耗时 |
|---|---|---|
| 周中随时 | 项目经理登记变更（A、B 段） | 3 分钟/条 |
| 会前 1 天 | 产品经理补 C 段 + 打预审标记 | 5 分钟/条 |
| 会前 2 小时 | 系统（现阶段是人工）汇总成"会前包" | 10 分钟 |
| 会上 | 补 D、E 段，逐条定级 | 5 分钟/条 |
| 会后当天 | 项目经理填 G 段：报价 + 确认时限 + 截止日 | 3 分钟/条 |
| 每周一 | 检查超期未确认清单，转"挂起"并通知项目经理 | 5 分钟 |
| 关闭时 | 补 F 段实际工作量与复盘 | 3 分钟 |

## 4. 定级规则

### 4.1 六维打分

| 维度 | 低（0） | 中（1） | 高（2） |
|---|---|---|---|
| 影响广度 | 1 个模块 | 2–3 个 | >3 个 / 跨系统 |
| 契约破坏 | 无 | 兼容新增 | breaking（字段/枚举/错误码） |
| 数据影响 | 无 | 加字段 | 需迁移历史数据 |
| 验收变化 | 新增 AC | 修改 AC | 删除 / 重定义 AC |
| 进度影响 | 不占关键路径 | 关键路径 <3 天 | 关键路径 >3 天 |
| 质量风险 | 覆盖良好 | 有缺口 | 核心链路 + 低覆盖 |

### 4.2 映射到等级

| 等级 | 判定 | 处理方式 |
|---|---|---|
| **L1 常规** | 任一维度不高于"中"，且无 breaking、无迁移 | 走常规迭代，**不开第二次会** |
| **L2 重要** | 有 1 项为"高"，或存在 breaking / 迁移 | 排期调整 + 明确回归范围 |
| **L3 重大** | ≥2 项为"高"，或涉及核心链路 + 数据迁移 | 重排里程碑 + 客户书面确认范围 |

**两条硬规则**（防止定级被稀释）：
- 契约 breaking → 至少 L2
- 需迁移历史数据 → 至少 L2

**反事实（建议等级必须附带）**：例如"若只改前端展示、不动订单金额，可降为 L1"。这句话能显著减少会上的争论，因为它把"能不能降级"变成可讨论的具体条件。

## 5. 观察期方案（2–3 周）

### 5.1 目标（只做三件事）

1. 拿到变更基线：量、类型分布、定级分布、估算偏差。
2. 验证会前材料是否被真正使用（会议时长、临时查代码次数）。
3. 攒出第一批"变更 → 模块"的对应数据，作为影响面模型的训练集。

### 5.2 明确不做的

- 不做影响面自动计算
- 不接入 Jira / 飞书 / 代码库
- 不改动任何现有审批流程
- 不承诺缩短工期

### 5.3 采集字段与用途映射

| 采集项 | 未来用在哪 |
|---|---|
| 客户原话 | 意图分类（澄清 / 变更 / 新增） |
| 变更类型 + 受影响模块 | 影响面图谱的第一批边 |
| 工作量（三档）vs 实际 | 估算校准系数 |
| 建议等级 vs 最终等级 + 改判理由 | 定级规则调参 |
| 从提出到定级的天数 | 变更响应时间基线 |
| **从定级到客户确认的天数** | 客户响应速度基线；也用来给"确认时限"定合理值 |
| **挂起数量与挂起时长** | 判断变更流程是否变成"客户拖延的垃圾桶" |
| 会议时长 / 参会人数 | 会前材料的 ROI 证据 |
| 是否产生线上问题 | 变更质量的事后验证 |

### 5.4 周报看什么（一页，周五出）

```
本周变更 7 条：新增 3 / 修改 3 / 澄清 1
定级分布：L1 4 · L2 2 · L3 1
挂起：2 条（超期未确认），其中 1 条挂满 10 天 → 已升级客户高层
报价：3 条需补充协议，合计 ¥18,000（不含税）
估算偏差：中位数 +38%（低估）
平均流转：提出 → 定级 4.2 天；定级 → 客户确认 5.8 天
会议：48 分钟（上周 65 分钟）
异常：CHG-1103 首次定 L2，会上改 L3（理由：涉及对账口径）
```

> 配套模板：`需求变更周报-模板.docx`（A4 一页，周五 17:00 前发出，抄送项目经理与产品经理）。数字从台账"统计"页直接抄，不手算。

### 5.5 进入自动化的判定标准

| 信号 | 阈值 | 说明 |
|---|---|---|
| 变更单完整率 | ≥ 80% | 填不全，后面全是脏数据 |
| 澄清类占比 | 观察值（预期 25–40%） | 占比越高，越该先做"意图初判" |
| 估算偏差中位数 | ≤ 40% | 偏差太大，说明影响分析本身不可靠 |
| 会前材料使用率 | ≥ 70% | 会上有人引用材料里的数字 |
| 会议时长变化 | 下降 ≥ 15% | 唯一能打动老板的指标 |

**五项里有三项达标**，再进入下一阶段；否则先修表单和口径。

### 5.6 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 填表负担 | 第二周开始糊弄 | 8 分钟原则 + 每字段标注"谁填/必填与否" |
| 口径不一 | 有人按"客户诉求"算一条，有人按"开发任务"算三条 | 在说明页写死"一次变更"的定义 |
| 定级形式化 | 全填 L2，没人看 | 强制"反事实"字段 + 每周抽 1 条复核 |
| 数据孤岛 | 填在 Excel，没人统计 | 台账自动汇总（见配套 xlsx 的统计页） |

### 5.7 "一次变更"的定义（必须写死）

> 同一客户诉求、在同一次沟通中提出、由同一个决策拍板的，算 **1 条变更**；若会上决定拆分实施，在"派生任务"里列子项，**不另开新单**。跨周的追加内容，另开新单并在备注中引用原单号。

## 6. 观察期之后（路线，不在本期范围）

1. **第 1 阶段（观察期后 2 周）**：变更单结构化入库 + 自动周报 + 会前包自动生成；跨项目汇总从"人工抄录"改为自动读取。
2. **第 2 阶段（1–2 月）**：代码侧契约快照（从路由/DTO/表结构反推），做 breaking 检测；变更单一键关联受影响模块。
3. **第 3 阶段（3 月+）**：影响面预测 + 定级建议 + 与 PR 审查打通（变更 → 切片 → PR → 用例失效）。

## 7. 已确认与待确认

**已确认（2026-11-09）**

| 决策 | 结论 |
|---|---|
| 报价方式 | 单价以合同约定为准，报价由项目经理人工核定后填写 |
| 报价口径 | **一律不含税**；含税项目在备注单独说明 |
| 客户确认时限 | **默认 5 个工作日** |
| 超期处理 | 超期未确认 → 变更**挂起**，不进入排期 |
| 升级机制 | 挂起满 **10 个工作日** → 标记需升级，项目经理上报客户高层 |
| 澄清类 | 由产品经理确认，不需客户签字 |
| 台账粒度 | 每个项目一份；跨项目**双周**人工合并，另用汇总模板 |
| 编号规则 | `项目代号-CHG-YYYYMMDD-NN` |
| 客户参会 | 不参会；项目经理过滤并转达，会上设"需转达客户的澄清项" |

**下一步（观察期第 1 周）**

1. 选一个变更最频繁的在途项目，复制 `变更台账-项目模板.xlsx`，填项目信息。
2. 通知项目经理：本周起所有变更（含澄清）先登记，只填 A、B 段。
3. 下次分析会前 1 天，产品经理补 C 段；会上按 E 段六维打分定级；会后填 G 段。
4. 周五出第一份周报，重点看两个数：**澄清占比**、**从定级到客户确认的天数**。

> 观察期内不追求数字好看，追求口径一致。第一周的绝对数一定不准，但**趋势从第二周就能看出问题**。
