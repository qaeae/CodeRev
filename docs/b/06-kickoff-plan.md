# 启动方案：先 B 后 A

> 版本 v1.0 ｜ 2026-11-09 ｜ 适用：2 周观察期 + 4 周 MVP

---

## 0. 结论

**先把 B（变更追溯与一致性）跑起来，两周后用它的数据决定 A（PR 审查）怎么做。**

| 维度 | 先做 B | 先做 A |
|---|---|---|
| 门槛 | Excel + 一张表单，明天就能开始 | GitHub App 审核 1–2 周，评测集 3–5 人日 |
| 见效 | 2 周能看到会议时长与变更量 | 4 周才有第一个可用版本 |
| 数据资产 | 变更 ↔ 模块的对应关系 | 只有 PR 与评论 |
| 差异化 | 客户拿不走（是他们自己的流程） | 容易被 CodeRabbit 平替 |
| 风险 | 团队不填表 | 审核被拒 / 误报率高 / 无种子客户 |

**代价**：A 晚 3 周启动。但这 3 周里 A 的外部依赖（App 审核、评测集、种子客户）同步推进，实际不晚——只是把"写代码"换成了"建资产"。

## 1. B 的两周执行表

| 时间 | 动作 | 产出 | 负责人 |
|---|---|---|---|
| D1 上午 | 选一个变更最频繁的在途项目；复制项目台账，填项目信息 | 台账就绪 | 你 |
| D1 下午 | 10 分钟宣讲：怎么填、什么时候填、挂起规则 | 团队知道要填 | 你 / 项目经理 |
| D2–D3 | 登记 3–5 条在途变更（只填 A、B 段） | 首批样本 | 项目经理 |
| D4 | 会前 1 天：产品经理补 C 段，打预审标记 | 会前材料 | 产品经理 |
| D5 | 分析会：补 D、E 段，逐条定级；会后补 G 段 | 首批定级结果 | 项目组 |
| D5 17:00 | 出第一份周报（只填第 1、2 段，其余写"试运行"） | 周报 v1 | 项目经理 |
| W2 周中 | 复盘口径：哪几个字段没人填、哪几个填错 | 表单修订 v1.1 | 你 |
| W2 周五 | 周报 v2 + 第一次估算校准（估算 vs 实际） | 周报 v2 | 项目经理 |
| W2 结束 | 五项验收打分，决定是否进入自动化 | 验收结论 | 你 |

## 2. B 的验收线与不达标怎么办

| 信号 | 达标线 | 不达标时先改什么 |
|---|---|---|
| 变更单完整率 | ≥ 80% | 砍字段：D 段从 9 行压到 3 行（模块、工作量、未知项） |
| 澄清占比 | 能解释（预期 25–40%） | 超过 50% 说明问题在需求侧，先出《客户澄清模板》，不是加功能 |
| 估算偏差中位数 | ≤ 40% | 改成区间估算（乐观/最悲观），先不做单点估计 |
| 会前材料使用率 | ≥ 70% | 把材料压到 1 页 3 个问题；仍不用就取消会前包 |
| 会议时长 | 下降 ≥ 15% | 检查是不是材料太长——超过 2 页一定没人看 |

**五项里三项达标 → 进入自动化；两项以下 → 只修表单和口径，不加任何功能。**

---

## 3. B → A 的数据交接

| B 产出的数据 | 在 A 里变成什么 | 对手有没有 |
|---|---|---|
| 变更单（结构化） | 需求/AC 的变更事件源，审查时可注入"本 PR 服务哪条 AC" | 没有 |
| 受影响模块清单 | 影响面图谱的第一批边，决定审查优先级 | 没有 |
| 估算 vs 实际 | 高风险模块识别（长期低估的模块优先审） | 没有 |
| 挂起 / 确认用时 | 交付风险信号，可进入 PR 摘要 | 没有 |
| 变更 ↔ PR 关联 | "这个 PR 是哪个客户需求的一部分"——审查报告可直接引用 | 没有 |

**一句话**：A 单独卖是"又一个 AI 审查工具"；接上 B 的数据，它才是"知道你这个 PR 该满足什么需求"的审查工具。这是唯一 CodeRabbit 短期抄不走的地方。

## 4. A 的启动判据

| 判据 | 最晚完成 |
|---|---|
| 评测集 200 个 PR + 标注 | W3 末 |
| GitHub App 提交审核 | W1 末（审核 1–2 周） |
| 单 PR 成本上限确定 | W2 末 |
| 3 家种子客户口头确认 | W3 末 |
| 4 周范围冻结（含不做清单） | W3 末 |
| PR-Agent LICENSE 快照归档 | W2 末 |

**W3 结束六条全绿 → W4 开写；缺两条以上 → 顺延一周，不硬上。**

---

## 5. 止损规则（提前写好，避免中途争论）

- B 两周后三项未达标：不加功能，只修表单；再给两周，仍不达标就放弃这条线。
- 澄清占比长期 > 50%：说明客户需求管理是根因，产品再改也没用，转为咨询服务。
- A 的评测集基线 precision < 40%：不做 SaaS，转内部工具或换垂直场景。
- GitHub App 审核被拒两次：改用 GitHub Actions + PAT 做内部试点，不阻塞验证。
- 种子客户 < 3 家：先做 B 的交付（咨询/流程），不投入 A 的研发。
