## 2. 仓库怎么用

### 分支模型

| 分支 | 放什么 | 谁能推 |
|---|---|---|
| `main` | 门户：全貌、上手、设计总览、索引 | 只有负责人合并 |
| `feat/b-change-trace` | B 轨道：变更管理全部文档与实现 | 参与者直接推 |
| `feat/a-pr-review` | A 轨道：PRD 与后续代码 | 参与者直接推 |

**规则**：任何改动先推子分支，**不要直接改 main**；合并到 main 由负责人确认后执行。

### 你的第一次提交

```bash
git clone git@github.com:qaeae/CodeRev.git
cd CodeRev
git checkout feat/b-change-trace        # 或 feat/a-pr-review
git checkout -b feat/b-<你的任务>        # 从子分支再切一个，别直接在共用分支上改
# ... 改文件 ...
git add -A
git commit -m "docs(b): 补充 XXX"
git push -u origin feat/b-<你的任务>
```

然后在 GitHub 上开 PR，目标分支选 `feat/b-change-trace`（不是 main）。

### 提交信息格式

```
<类型>(<范围>): <一句话>

类型：docs | feat | fix | chore | refactor
范围：a | b | design
例：docs(b): 补充挂起升级的判定条件
```

## 3. 本地环境

| 需要 | 用途 | 备注 |
|---|---|---|
| Git | 版本控制 | 已有 SSH key 可直接 clone |
| Python 3.11+ | 生成 docx/xlsx（可选） | 只有要改模板排版时才需要 |
| Node 18+ | 后续 A 的开发 | 现在用不到 |

**注意**：`assets/` 里的 docx/xlsx 是**产物**，正文以 `docs/` 下的 Markdown 为准。改文档请改 md，不要直接改 Office 文件——否则下次生成会被覆盖。

生成脚本在仓库外的 `tools/` 目录（本地保留，不入库），需要时找负责人要。

## 4. 你能立刻帮上的三件事

| 任务 | 需要什么 | 产出 |
|---|---|---|
| **记录变更** | 熟悉一个在途项目 | 每周 3–5 条变更单，填 A、B 段 |
| **整理口径** | 细心 | 检查台账/周报/汇总三处口径是否一致 |
| **A 的评测集** | 能判断代码好坏 | 200 个真实 PR 的人工标注（真问题/非问题/级别） |

第三件事门槛最高但价值最大——**它是 A 能不能开工的前提**。

## 5. 这个项目的三条潜规则

1. **口径写在文档里，不靠口头传**。数字口径（不含税、5 个工作日、10 天升级）改动必须同时改台账、周报、汇总三处。
2. **表单超过 8 分钟没人填**。任何新增字段，先问"能不能砍掉一个旧的"。
3. **不追求数字好看，追求口径一致**。第一周的数据一定不准，趋势从第二周才看得出来。
